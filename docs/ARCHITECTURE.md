# Автономка — архітектура сайту

Один документ з описом того, як влаштований сайт: звідки беруться дані, як вони
перетворюються на HTML, як влаштована багатомовність, кошик і замовлення, і що
саме автоматизовано. Замінює застарілий `docs/avtonomka-automation.md` (той
описував інший GitHub-акаунт власника репо і сервер з cron, якого вже немає —
деплой зараз іде через GitHub Pages, див. розділ 6).

Актуально на 2026-09-02. Репозиторій: `dfi-company/avtonomka_site`, гілка `master`.

---

## 1. Що це за сайт

Статичний інтернет-магазин обладнання для автономного живлення (гібридні
інвертори, акумулятори LiFePO4, комплекти інвертор+акумулятор, силові й сонячні
кабелі, ДБЖ/зарядні станції). Без бекенду й без білд-кроку для більшості файлів —
чистий HTML + vanilla JS, хоститься на GitHub Pages.

Окремо існує **Telegram міні-застосунок** у `miniapp_v/` — самостійний проєкт зі
своїм каталогом фото (`miniapp_v/photos/`, `miniapp_v/felicity-fla48314/`) і своєю
`index.html`. Він читає той самий `products.json`, але **ніколи не показує
зелені сайтові фото комплектів як запасний варіант** — лише власні "темні"
фото з `miniapp_v/photos/manifest.json`, інакше показує заглушку. Це свідоме,
постійне правило.

## 3. Щоденна автоматизація (GitHub Actions)

**Файл:** `.github/workflows/update.yml`. Розклад `0 6 * * *` (06:00 UTC =
09:00 Київ) + можливість запустити вручну (`workflow_dispatch` /
`gh workflow run update.yml`).

Job **update-data**:
1. `python scripts/fetch_feed.py` — тягне `https://dfi2.com.ua/price_xml/avtonomka.txt`,
   зберігає в `products.json`. При цьому:
   - переносить `description`/`link`/`embed`/`specs`/`slug` зі старого
     `products.json`, щоб ручні правки не губились при кожному запуску;
   - якщо в `assets/images/komp/<id>.*` або `assets/images/products/<id>_*.*`
     є локальний файл — підміняє ним `image_link`/`additional_images` замість
     посилання постачальника (`dfi2.com.ua`);
   - комплектам без локального фото ставить `assets/images/zaglushka.png`
     (зовнішнє посилання на фото комплекту ніколи не використовується);
   - застосовує знижки з `price_adjustments.json`;
   - генерує білінгвальні SEO-ключові слова (`generate_seo_keywords.py`) в
     `merchant_keywords_uk`/`_ru`.
2. `python scripts/fetch_telegram.py` — парсить публічну веб-версію
   `t.me/s/avtonomka_od`, зберігає до 30 останніх постів у
   `data/telegram_posts.json`.
3. `node scripts/export_to_csv.js` → `catalog_export.csv` (для Google Sheets).
4. `node scripts/generate_merchant_feed.js` → `feed.xml` (RSS 2.0 + Google
   Shopping namespace, доступний на `https://avtonomka.com.ua/feed.xml`).
5. `node scripts/generate_static_pages.js` — див. розділ 4.
6. Коміт `chore: update products and posts [дата]` (тільки якщо щось
   реально змінилось) і пуш.

Job **deploy** (залежить від update-data): вивантажує весь корінь репо як
GitHub Pages artifact і деплоїть. Тобто зміни з кроку 6 одразу йдуть на
живий сайт — окремого серверного cron/git pull більше немає.

**Важливо:** `node` і `npm` недоступні в звичайному sandbox-середовищі
розробки — кроки 3–5 виконуються лише в CI. Локально їх можна лише
редагувати текстом, не запускати.

## 4. Пре-рендер для пошукових ботів (`generate_static_pages.js`)

Проблема, яку він вирішує: `catalog.html`, `product.html` (стара `?id=`
версія) й фактично всі списки на сайті раніше рендерились **тільки** через
client-side JS з `products.json`/`data/*.json` — view-source показував
порожній `<div>` і спінер. Для ботів, що не виконують JS (і навіть для
Googlebot — це "друга хвиля" індексації), це погано.

Скрипт (запускається щодня в CI, крок 5 з розділу 3) запікає готовий HTML:

1. **Товари:** для кожного товару — `product/<slug>/<id>.html` зі
   справжніми title/price/availability/description і JSON-LD
   Product/Offer розміткою. Стара плоска URL `product/<id>.html`
   лишається як redirect-заглушка (і продубльована правилом у `.htaccess`,
   яке теж перегенеровується щоразу).
2. **Сітки каталогу:** перша сторінка (сортування за замовчуванням, без
   фільтрів — те, що показує `catalog.js` при першому завантаженні) для
   `catalog.html` і кожного `catalog/<slug>.html`, обгорнута в
   `<!-- SSR:START/END -->` — повторні запуски ідемпотентні (заміняють
   вміст між маркерами, а не дублюють).
3. **Telegram-стрічка й статті:** те саме для `blog.html` (`#blog-grid`),
   `articles.html` (`#articles-grid`) і двох прев'ю на головній
   (`#home-tg-feed`, `#home-articles-grid`) — маркери
   `SSR:TG` / `SSR:ARTICLES` / `SSR:HOME-TG` / `SSR:HOME-ARTICLES`. Це лише
   список карток (заголовок, дата, summary) — повний текст статті
   відкривається через JS hash-роутинг (`articles.html#slug`) і не має
   власної URL, тому не пре-рендериться.
4. `sitemap.xml` — перебудовується повністю з нуля щоразу (товари +
   категорії + статичні сторінки), `<lastmod>` береться з git-історії
   файлу або з сьогоднішньої дати, якщо файл змінився в цьому ж запуску.
5. `.htaccess` — по одному `RewriteRule` на кожен товар (стара плоска URL
   → нова `/product/<slug>/<id>.html`).

**Важливий наслідок:** будь-яка логіка рендеру картки товару/поста/статті
існує одразу в **кількох місцях**, які тримаються в синхроні вручну:
`assets/js/catalog.js` (клієнт), `assets/js/product.js` (клієнт),
`assets/js/blog.js` / `assets/js/articles.js` (клієнт) і
`scripts/generate_static_pages.js` (SSR-копія тих самих функцій). Коли
міняється вигляд картки (нова плашка, інший текст кнопки) — правити треба
у **всіх** місцях, інакше SSR-версія й клієнтський рендер розійдуться.
Оскільки `node` локально недоступний, SSR-частину для новин/статей
доводиться імітувати вручну Python-скриптом з тією самою логікою заміни
між SSR-маркерами (не зберігається в репо — одноразовий).

## 5. Клієнтський JS (`assets/js/`)

| Файл | Роль |
|---|---|
| `i18n.js` | Завантажує `translations/<lang>.json`, застосовує `data-i18n`/`data-i18n-placeholder`/`data-i18n-aria`/`data-i18n-html` атрибути, будує перемикач мови, виставляє `window.I18n` (`t()`, `productTitle()`, `productDesc()`) |
| `main.js` | Бургер-меню, лайтбокс фото, лічильник переглядів статей (Abacus) |
| `catalog.js` | Список товарів категорії: фасетні фільтри (потужність/бренд/ємність/переріз/довжина/накінечник/монобренд), сортування, пагінація, картки з плашками |
| `product.js` | Сторінка товару: галерея, опис, плашки (ті самі, що на картці каталогу), редірект зі старої `product.html?id=` на нову статичну URL |
| `articles.js` | Список статей + повний перегляд статті через `#hash`-роутинг, лічильник переглядів, блок "Схожі товари" |
| `blog.js` | Рендер Telegram-постів на `blog.html` і в прев'ю на головній |
| `cart.js` | Кошик у `localStorage` (`avtonomka_cart`), плаваюча кнопка |
| `checkout.js` | Сторінка `checkout.html`: форма доставки Новою Поштою, відправка в Google Apps Script |
| `order-form.js` | Спливна форма швидкого замовлення (кнопка "Замовити" на сторінці товару) — той самий бекенд, що й checkout |
| `legal.js` | Допоміжне для юридичних сторінок |

### Плашки товару (badge-stack)

Один стек невеликих кольорових плашок над фото картки/сторінки товару,
логіка однакова в `catalog.js`/`product.js`/`generate_static_pages.js`:

- **ТОП** — не випадково по `Math.random()`, а детермінований хеш id
  (`hash % 4 === 0`, ≈20-25% товарів), щоб один і той самий набір лишався
  "топовим" при кожному перезавантаженні сторінки, а не тасувався.
- **Комплекти:** "+ Розстрочка", рівень запасу "Легкий/Оптимальний/Супер
  запасливий" (за ємністю акумулятора: ≤5 / ≤12 / >12 кВт·год), "Один
  бренд <Brand>" якщо інвертор і акумулятор одного виробника.
- **Кабелі:** переріз (⌀), розмір накінечника (🔩), довжина (📏) —
  витягуються регексами з назви товару.
- **Інше:** наявність ("✓ В наявності" / "Немає").

## 6. Багатомовність (UK/EN)

- `translations/uk.json` / `en.json` — вкладені namespace-и (`nav`,
  `footer`, `home`, `catalog`, `product`, `articles`, `blog`, `checkout`,
  `order_form`, `404`). Ключі мають **повністю збігатись** між UK і EN
  (крім `*.page_title`, який є лише в EN — UK бере заголовок прямо з
  `<title>` в HTML).
- Мова визначається з `?lang=` в URL → `localStorage('lang')` → `uk` за
  замовчуванням.
- `translations/products.en.json` — окремий масив `{id, title_en,
  description_en}` для перекладу карток товару (підвантажується лише коли
  обрано EN).
- Кожен JS-модуль, що будує HTML з перекладеним текстом, має власну
  локальну функцію `t(key, vars)` (не імпортується — кожен файл
  самодостатній) і **обов'язково чекає на `i18n:ready`** перед першим
  рендером, інакше `t()` поверне сирий ключ замість перекладу (`window.I18n`
  з'являється асинхронно).
- `data-i18n-html="true"` — єдиний спосіб перекласти текст з вкладеним
  посиланням (наприклад, згода з політикою конфіденційності): значення в
  JSON вже містить `<a href="...">`, тому елемент з цим атрибутом має бути
  "листовим" (без інших дітей типу чекбоксів), інакше `innerHTML =`
  затре їх.

## 7. Кошик і замовлення

Два незалежні шляхи оформлення, обидва пишуть в **одну** Google Таблицю
через **один** Google Apps Script Web App (`scripts/order_form_apps_script.gs`):

1. **Кошик → checkout.html** (`assets/js/cart.js` + `checkout.js`) — повна
   форма з доставкою Новою Поштою (місто, відділення, спосіб оплати).
2. **Швидка заявка** (`order-form.js`, кнопка "Замовити" на сторінці
   товару) — лише ім'я/телефон/коментар, без доставки.

Обидва передають поле `source` (`"Сайт"`), і мобільний **міні-застосунок**
(`miniapp_v/index.html`) шле третій потік з `source: "Мініапп"` на **той
самий** Apps Script endpoint — усі три джерела пишуться в один аркуш
"Заявки" з колонкою "Джерело" для розрізнення.

Apps Script приймає і `application/x-www-form-urlencoded` (сайтові форми),
і сирий JSON-текст (міні-апп), бо `no-cors` fetch з різних клієнтів
серіалізує тіло по-різному. **Зміна коду `.gs`-файлу не застосовується
автоматично** — вимагає ручного "New deployment version" у Google Apps
Script Editor (Claude не має доступу до Google-акаунту, щоб зробити
це самостійно).

## 9. Supabase (коментарі, статті)

Перша "база даних" сайту — окремий, безкоштовний бекенд-сервіс
[Supabase](https://supabase.com) (Postgres з готовим REST API), а не власний
сервер. Сайт лишається статичним, лише додався ще один зовнішній API поряд з
Google Apps Script (розділ 7) і Abacus (лічильник переглядів статей). Проєкт:
`uvndubhmqzqqsrnrxgaj` (URL і anon-ключ уже вписані в код, реальні - не
плейсхолдери).

Безпеку дає не секретність ключа (`anon` ключ навмисно публічний і зашитий
прямо в JS), а політики Row Level Security на рівні бази.

### 9.1. Коментарі клієнтів

**Схема:** `scripts/supabase/comments_schema.sql` — таблиця `comments`
(`product_id`, `author_name`, `text`, `approved`, `created_at`):
- анонімний відвідувач сайту може **вставити** новий коментар (завжди
  `approved = false`) і **читати** лише вже схвалені;
- автентифікований адмін бачить усі коментарі й може їх схвалювати чи
  видаляти.

**Клієнтська частина:** `assets/js/comments.js` - підключений і на
`product.html` (шаблон), і на кожній пре-рендереній `product/<slug>/<id>.html`
сторінці. Сам будує розмітку блока коментарів (заголовок, список, форма) і
вставляє її після `.product-layout` - жодної статичної розмітки в HTML не
потрібно, тому одна зміна в `comments.js` одразу діє скрізь.

### 9.2. Статті

Раніше — `data/articles.json`, редаговане через `admin.html` і GitHub
Contents API (коміт у репо → чекати деплой). Тепер стаття зберігається в
таблиці `articles` (схема + міграція наявних 8 статей: `scripts/supabase/
articles_schema.sql`) і читається напряму з Supabase - без GitHub і без
очікування деплою:
- будь-хто читає всі статті (`anon can read articles`);
- писати (створювати/редагувати/видаляти) може лише автентифікований адмін.

Читають цю таблицю: `assets/js/articles.js` (сторінка `articles.html`),
`index.html` (інлайн-скрипт "Останні статті"), і `scripts/
generate_static_pages.js` (SSR-блоки `articles.html`/`blog.html`/`index.html`
+ "Читайте також" на кожній сторінці товару - той самий Node-скрипт тепер
робить `fetch()` до Supabase REST API замість читання локального файлу, тому
весь генератор став асинхронним).

### 9.3. Модерація й редагування (admin.html)

Один спільний Supabase-логін (email/пароль користувача, створеного в
Supabase Dashboard → Authentication → Users - окремо від локального пароля
самої адмінки) відкриває одразу і "Статті" (список + редактор), і "Коментарі
клієнтів" (список несхвалених із кнопками "Схвалити"/"Видалити"). Картка
"Налаштування GitHub" (GitHub PAT-токен) прибрана - вона керувала лише
`data/articles.json`, якого більше нема.

### 9.4. Віртуальні товари для SEO/індексації

Таблиця `virtual_products` (схема + міграція: `scripts/supabase/
virtual_products_schema.sql`) - товари, яких немає в реальному фіді
постачальника (`products.json`), додані вручну для пошукового трафіку за
суміжними моделями. **Не справжня наявність** - кожен `id` і `title`
має префікс `V` (напр. `V142724`, "V Гібридний інвертор..."), щоб було
видно, що товар не реальний.

Джерело: одноразовий імпорт `/home/tetiana/Downloads/prd_avto.xlsx` (256
рядків від постачальника dfi.ua). З них 46 співпали за id і 1 за назвою

209 записів. Фото перезалиті під власний домен

товару з цього ж імпорту (той самий бренд/категорія) як заглушку. Опис -
шаблонний, згенерований з характеристик у назві (потужність/напруга/
ємність/вага), не написаний вручну для кожного товару.

RLS - той самий патерн, що й `articles`, але з поправкою на `active`:
`anon` бачить лише `active = true` (керується з `admin.html`), автентифікований
адмін - усі рядки. Пише лише адмін.

**Де вони показуються (рішення від 2026-09-03):**

- **Окремі сторінки** `product/<slug>/<id>.html` - генеруються
  `scripts/generate_static_pages.js` разом з реальними товарами, для

- **Каталог сайту** (`catalog.html`, `catalog/*.html`, пошук,

### 9.5. ⚠ avtonomka.com.ua не деплоїться автоматично з GitHub Pages

Виявлено 2026-09-02: `avtonomka.com.ua` обслуговується окремим сервером
(LiteSpeed/CyberPanel), не GitHub Pages. GitHub Pages-версія
(`dfi-company.github.io/avtonomka_site`) оновлюється справно щоразу, коли
спрацьовує `update.yml` (розділ 3), а ось файли на `avtonomka.com.ua` не
змінювались із 26 серпня - схоже, зупинився серверний cron
(`git pull` на хості), який мав підтягувати зміни щодня. Це означає, що весь
цей документ описує GitHub-репозиторій і GitHub Pages, а не обов'язково
те, що зараз реально бачать відвідувачі `avtonomka.com.ua`. Потребує
розслідування з боку власника (доступ до сервера є лише в нього) - або
відновити серверний cron, або перенаправити домен напряму на GitHub Pages.
