# План реалізації: аукціон для Автономки

Джерело: обговорення в Telegram (2026-09-15), ідея — продавати вживані/з
дефектом товари у форматі аукціону з таймером, кроком ставки, обов'язковою
реєстрацією клієнта і окремою (можливо не проіндексованою) сторінкою.

Це план, не код. Розписано архітектуру, модель даних і етапи — постав
позначки/правки прямо в тексті, де хочеш щось змінити.

---

## 0. Вихідні вимоги (з чату)

- Лот з початковою ціною.
- Можливість коригувати крок підвищення ставки (мінімальний інкремент).
- Клієнт обов'язково реєструється і лишає свої дані перед тим, як ставити.
- Таймер до завершення лоту.
- Видно останню (поточну найвищу) ставку.
- Виводити лот на сайт (публікувати) + додавати фото і відео — **тільки
  для нас**, не для клієнтів (тобто функція адмінки, не публічна форма).
- Можливо окрема вкладка на сайті, можливо закрита й не проіндексована.

## 1. Рішення, які варто підтвердити (я взяв дефолти — виправ, що не так)

1. **Реєстрація** — ім'я + телефон (як у швидкій формі замовлення зараз),
   без SMS-підтвердження. Досить для MVP чи потрібна перевірка номера?  - НІ
2. **Скільки лотів одночасно** — план розрахований на кілька паралельних
   активних лотів (список + сторінка лота). Якщо насправді завжди буде
   один лот за раз — список можна спростити/прибрати. - ДЕКІЛЬКА
3. **Анти-снайпінг** — якщо хтось ставить у останні секунди, чи треба
   автоматично продовжувати таймер (наприклад +2 хв)? За замовчуванням
   у плані цього немає (просто жорсткий дедлайн) — додати нескладно, якщо
   потрібно. - НІ
4. **Після завершення аукціону** — переможець визначається вручну
   адміном (дивиться найвищу ставку і телефонує), так само як зараз
   обробляються замовлення. Автоматичної оплати/чекауту в MVP немає. - ТАК
5. **Видимість сторінки** — за дефолтом: жодного посилання в шапці/футері
   сайту, `noindex`, доступ лише по прямому лінку (наприклад, з поста в
   Telegram-каналі). Якщо треба пункт меню — легко додати окремим кроком. - ТАК
6. **Публічність ставок** — за дефолтом видно суму поточної найвищої
   ставки і коротке ім'я лідера (напр. "Ірина К."), повна історія останніх
   ставок теж публічна (без телефонів). Телефон/повне ім'я бачить лише
   адмін. - МОЖНА ДАТИ ЇМ ПРОСТО ЩОСЬ ТИПУ "УЧАСНИК 1, УЧАСНИК 2"

## 2. Чому саме так — коротко про архітектуру

Сайт статичний (GitHub Pages), без бекенду. Єдиний "справжній" бекенд, який
вже є в проєкті — **Supabase** (Postgres + RLS), він уже обслуговує
коментарі й статті (`docs/ARCHITECTURE.md`, розділ 9). Аукціон логічно
лягає туди ж:

- дані лотів/ставок — нові таблиці в тому ж Supabase-проєкті;
- фото/відео лотів — новий **Supabase Storage bucket** (перший випадок
  використання Storage в проєкті; зараз фото товарів лежать у репо й
  деплояться через git — для аукціону це занадто повільно, потрібне
  миттєве оновлення без чекання на GitHub Pages);
- реалтайм оновлення ставки для всіх, хто дивиться лот — **Supabase
  Realtime** (підписка на зміни в таблиці ставок), той самий рушій, що й
  для БД;
- адмінка — новий таб у вже існуючому `admin.html` (той самий
  Supabase Auth логін, що й для статей/коментарів);
- публічні сторінки — нові `auction.html` / `auction-lot.html`, чистий
  client-side рендер (як `comments.js`), **без** участі в
  `generate_static_pages.js` — сторінка не для SEO, тож не варто тягнути
  її в SSR-пайплайн і множити місця, де дублюється логіка (розділ 4
  ARCHITECTURE.md прямо попереджає про цю пастку).
  - потрібно створити окрему адмінку , яка не буде мати доступу у базу, але буде мати доступ ставити лоти і публікувати їх і буде могти бачити людей які ставлять ставки (повну інфу)

## 3. Модель даних (Supabase)

Новий файл `scripts/supabase/auction_schema.sql` (за зразком
`comments_schema.sql` / `virtual_products_schema.sql`).

### `auction_lots` — лоти

| Поле | Тип | Опис |
|---|---|---|
| `id` | bigint identity PK | |
| `slug` | text unique | для URL `auction-lot.html?id=<slug>` |
| `title` | text | |
| `description` | text | |
| `condition_note` | text | опис дефекту/стану (те, чому це аукціонний товар) |
| `media` | jsonb | `[{type:"photo"\|"video", url:"..."}]`, файли в Storage |
| `starting_price` | numeric | |
| `bid_step` | numeric | мінімальний крок ставки |
| `current_price` | numeric | грошовий стан — дублюється тут, оновлюється атомарно функцією `place_bid` |
| `leader_bid_id` | bigint null | FK на поточну найвищу ставку |
| `status` | text | `draft` \| `active` \| `cancelled` (заголовок "finished" не окремий статус — рахується як `active` і `ends_at < now()`) |
| `starts_at` | timestamptz null | |
| `ends_at` | timestamptz | дедлайн |
| `created_at` | timestamptz | |

### `auction_bidders` — зареєстровані учасники

| Поле | Тип | Опис |
|---|---|---|
| `id` | uuid PK (`gen_random_uuid()`) | зберігається в `localStorage` клієнта після реєстрації, щоб не реєструватись на кожну ставку |
| `name` | text | |
| `phone` | text | |
| `email` | text null | |
| `consent` | boolean | згода на обробку даних (той самий текст, що в checkout/order-form) |
| `created_at` | timestamptz | |

**RLS:** `anon` може лише **INSERT**, без SELECT (щоб ніхто не міг
переглянути чужі телефони через API). SELECT — лише `authenticated`
(адмін).

### `auction_bids` — ставки

| Поле | Тип | Опис |
|---|---|---|
| `id` | bigint identity PK | |
| `lot_id` | bigint FK → `auction_lots` | |
| `bidder_id` | uuid FK → `auction_bidders` | |
| `display_name` | text | зберігається тут окремо від `auction_bidders`, напр. "Ірина К." — щоб публічний SELECT цієї таблиці ніколи не діставав телефон |
| `amount` | numeric | |
| `created_at` | timestamptz | |

**RLS:** `anon` має **SELECT** (публічна історія ставок), але **не** має
прямого INSERT — вставка лише через RPC-функцію нижче. Це і є захист від
невалідних ставок.

### RPC-функція `place_bid(p_lot_id, p_bidder_id, p_amount)`

`SECURITY DEFINER`, єдиний легальний спосіб поставити ставку:

1. `SELECT ... FOR UPDATE` на рядок лота (блокує від гонки двох
   одночасних ставок).
2. Перевіряє `status = 'active'` і `now() < ends_at`.
3. Перевіряє `p_amount >= current_price + bid_step`.
4. Вставляє рядок в `auction_bids` (з `display_name`, підтягнутим із
   `auction_bidders`).
5. Оновлює `auction_lots.current_price` і `leader_bid_id`.
6. (опційно, якщо вирішимо за п.3 розділу 1) продовжує `ends_at`, якщо
   ставка в останні N секунд.
7. Повертає новий стан лота або помилку ("хтось щойно перебив ставку").

Це вирішує головний ризик прямого доступу через публічний `anon`-ключ:
без цієї функції клієнт міг би вставити будь-яку суму напряму в таблицю.

### Storage bucket `auction-media`

Публічний бucket (SELECT — всім, INSERT/DELETE — лише `authenticated`),
аналогічно тому, як уже влаштований доступ до таблиць. Налаштовується
вручну в Supabase Dashboard (як і Auth-користувач для адмінки — одноразова
дія, Claude не має туди доступу).

## 4. Адмінка (`admin.html`)

Новий таб "Аукціон" поруч із наявними "Статті" / "Коментарі" (той самий
Supabase-логін):

- **Список лотів** — статус, поточна ціна, час до завершення, к-сть ставок.
- **Створити/редагувати лот** — назва, опис, опис стану/дефекту,
  початкова ціна, крок ставки, дедлайн, завантаження фото/відео (в
  `auction-media` bucket), статус (`draft`/`active`/`cancelled`).
- **Перегляд ставок лота** — таблиця ставок (сума, час, ім'я), і, лише
  тут, телефон лідера (join з `auction_bidders`, видно тільки
  `authenticated`) — щоб адмін міг зв'язатись із переможцем після
  завершення.

## 5. Публічні сторінки

- **`auction.html`** — список активних (і, за бажанням, завершених) лотів:
  фото, назва, поточна ціна, залишок часу.
- **`auction-lot.html?id=<slug>`** — галерея фото/відео, опис, поточна
  ціна + крок, таймер, форма ставки, стрічка останніх ставок.
- **`assets/js/auction.js`** — новий клієнтський модуль за тим самим
  патерном, що й `comments.js`: чекає `i18n:ready`, сам будує розмітку,
  підписується на Supabase Realtime канал ставок цього лота (з fallback
  на періодичний polling кожні ~5 с, якщо Realtime недоступний).
- **Реєстрація** — модалка з'являється при першій спробі поставити ставку,
  якщо в `localStorage` ще немає `bidder_id`. Після реєстрації id
  зберігається локально й перевикористовується для наступних ставок.
- **Таймер** — `setInterval` до `ends_at`, після завершення форма ставки
  блокується (і сервер однаково відхилить ставку через RPC).

### SEO/індексація

- `<meta name="robots" content="noindex,follow">` (як у `checkout.html`).
- `robots.txt` — додати `Disallow: /auction.html` і `/auction-lot.html`
  (за дефолтом з п.5 розділу 1 — переглянь, якщо вирішиш дати сторінці
  посилання з меню).
- Не входить у `sitemap.xml` і не чіпає `generate_static_pages.js` —
  сторінка суто client-side, без SSR.

## 6. Етапи реалізації

1. **Backend-фундамент** — SQL-схема (`auction_schema.sql`: таблиці, RLS,
   `place_bid()`), Storage bucket + політики, увімкнути Realtime-реплікацію
   для `auction_lots`/`auction_bids` (все — ручні кроки в Supabase
   Dashboard, як і попередні рази).
2. **Адмінка** — таб "Аукціон": CRUD лотів, завантаження медіа, перегляд
   ставок і контактів.
3. **Публічні сторінки** — список + сторінка лота, таймер, форма ставки,
   реєстрація.
4. **Реалтайм** — підписка на оновлення ставок/ціни без перезавантаження
   сторінки.
5. **SEO-виключення** — noindex, robots.txt, без пункту меню.
6. **Ручний флоу після завершення** — адмін дивиться переможця в адмінці й
   зв'язується сам (без автоматизації оплати/доставки в MVP).

Етапи 1–3 — мінімум для робочого MVP (можна тестувати з одним лотом уже
без п.4/5, просто оновлюючи сторінку вручну). П.4–6 — доводка.

## 7. Поза межами MVP (свідомо не робимо зараз)

- Онлайн-оплата/автоматичний чекаут переможця.
- SMS/email-підтвердження реєстрації.
- Анти-снайпінг (автопродовження таймера) — якщо не підтвердиш у п.3
  розділу 1.
- Публічний профіль учасника / історія його ставок по всіх лотах.
- Автоматичне архівування/видалення завершених лотів.
